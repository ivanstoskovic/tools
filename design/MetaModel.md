# 1. Purpose

This document defines the canonical object model of the Stoleus Framework.

Every architectural decision, subsystem, provider, module and command derives from the concepts defined here.

The Meta Model is the highest-level technical document of the framework.

It defines **what exists** inside the framework.

It intentionally does not define implementation details.

Those are specified in the SFS documents.

---

# 2. Motivation

Large frameworks remain maintainable because they share a stable vocabulary.

Examples include:

- .NET
- Kubernetes
- Terraform
- Spring
- ASP.NET Core

Each defines a small set of first-class concepts.

Everything else is built upon those concepts.

The Stoleus Framework follows the same principle.

---

# 3. Core Principles

The framework is built upon the following principles.

## P1

Metadata first.

The framework always reasons about metadata before implementations.

---

## P2

Implementations are passive.

The framework orchestrates execution.

Plugins never orchestrate each other.

---

## P3

Contracts define behavior.

Implementations fulfill contracts.

---

## P4

Providers abstract platforms.

Modules never depend on operating systems.

Modules depend only on contracts.

---

## P5

Definitions are immutable.

After registration, framework metadata never changes.

---

## P6

Discovery precedes execution.

The framework completely understands the environment before executing anything.

# 5. PluginDefinition

## Purpose

Defines a plugin without executing it.

---

## Responsibilities

- Identity
- Metadata
- Dependencies
- Capabilities
- Lifecycle entry points
- Contract requirements

---

## Invariants

- Immutable after registration.
- Contains no executable behavior.
- Independent of implementation language.

---

## Relationships

Consumes:

- Manifest

Produces:

- Registry Entry

Used by:

- Dependency Engine
- Execution Engine
- CLI
- Documentation Engine

---

# 6. Registry

## Purpose

The Registry is the canonical catalog of the framework.

Every subsystem reads from it.

No subsystem modifies it after bootstrap.

---

## Responsibilities

- Store PluginDefinitions
- Store Contracts
- Store Capabilities
- Store Dependencies
- Store Metadata

---

## Invariants

Read-only after bootstrap.

---

# 7. DependencyGraph

## Purpose

Represents relationships between PluginDefinitions.

---

## Responsibilities

- Dependency validation
- Cycle detection
- Topological ordering

---

## Produces

ExecutionPlan

---

# 8. ExecutionRequest

Represents user intent.

Examples:

```
stoleus setup docker
```

```
stoleus verify firewall
```

ExecutionRequest does not contain an execution order.

---

# 9. ExecutionPlan

Represents the ordered execution generated by the Dependency Engine.

ExecutionPlans are immutable.

ExecutionPlans may be visualized, validated or executed.

---

# 10. Lifecycle

The framework lifecycle consists of six phases.

```
Discover

↓

Validate

↓

Plan

↓

Execute

↓

Verify

↓

Report
```

Modules may define lifecycle operations within the Execute phase.

---

# 11. Contract

Contracts define framework behavior.

Providers implement contracts.

Modules consume contracts.

The framework resolves contracts.

---

# 12. Provider

Providers abstract platform-specific behavior.

Examples include:

- Package Manager
- Service Manager
- Firewall
- Filesystem
- Logger
- Documentation

---

# 13. Module

Modules implement infrastructure functionality.

Examples include:

- Chrony
- Docker
- Firewall
- PostgreSQL
- GitHub Runner

Modules never call operating-system commands directly.

They use Contracts.

---

# 14. Command

Commands expose framework functionality to users.

Commands translate CLI input into ExecutionRequests.

Commands never execute infrastructure directly.

---

# 15. Context

Execution occurs within one or more contexts.

Examples:

- ExecutionContext
- PlatformContext
- ConfigurationContext
- LoggingContext
- SecurityContext

Contexts are immutable during a single execution.

# 17. Framework Invariants

The following rules are never violated.

1. Plugins never execute plugins.
2. Providers never execute modules.
3. Modules never know operating systems.
4. Contracts define interactions.
5. Definitions are immutable.
6. Discovery completes before execution begins.
7. Execution always follows an ExecutionPlan.
8. The Registry becomes read-only after bootstrap.
9. Providers implement Contracts.
10. Modules consume Contracts.
